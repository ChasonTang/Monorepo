## 1. Purpose and design rationale

This RFC proposes `argcv_validate_ipv4`, a public predicate for validating a
complete byte slice as a strict dotted-decimal IPv4 address. Its grammar is
already implemented by the private `validate_ipv4_tail` helper in
[value.c](../value.c). The public API makes that validation available to
callers that need to check IPv4 independently of IPv6 parsing.

The design defines the API contract and the tests needed to establish it.
Validation checks syntax only. Splitting a host from a port, choosing between
IPv4, IPv6, and hostname validation, and deciding whether to connect to an
accepted address remain the caller's responsibility.

## 2. Public API and contract

Add the following declaration to `argcv/value.h`, inside the existing C
linkage and nonnull annotation regions:

```c
ARGCV_EXPORT bool argcv_validate_ipv4(const char *text, size_t len);
```

### 2.1 Input storage and slice boundaries

`text` must be a valid nonnull pointer with at least `len` readable bytes,
including when `len == 0`. The storage must remain valid and its contents
unchanged throughout the call. Concurrent readers are allowed; the caller
must prevent conflicting writes.

These are preconditions, not syntax rules. Calls that violate them are outside
the contract and must not be used as negative tests expecting `false`.

The input consists of exactly `len` bytes starting at `text`. The function
must neither read beyond that slice nor let bytes outside it affect the
result. No NUL terminator is required. When passing a C string, exclude its
terminator from `len`; a NUL anywhere inside the slice is invalid. An empty
slice returns `false` without reading any input bytes.

### 2.2 Accepted syntax

For a call that satisfies the preconditions, the result is `true` if and only
if the entire slice matches this grammar:

```text
IPv4 ::= OCTET "." OCTET "." OCTET "." OCTET
```

Each `OCTET` is the ASCII decimal representation of an integer from 0 through
255. It contains one to three digits and has no leading zero unless it is
exactly `0`. Each separator is an ASCII dot. Every valid representation is
therefore 7 to 15 bytes long, inclusive; being within that range is not enough
to establish validity.

All other inputs return `false`. This excludes abbreviated forms, a single
integer representing the address, hexadecimal notation, signs, whitespace,
non-ASCII bytes, and any extra content before or after the address. Validation
does not trim, decode, or otherwise normalize input.

There are no restrictions on address values beyond the grammar. In
particular, `0.0.0.0`, `255.255.255.255`, and loopback, private, link-local, and
multicast addresses are accepted. Their suitability for a particular use is
outside this API's scope.

### 2.3 Results and side effects

The boolean is the entire result. The API provides no partial parse result
or output parameter. It leaves input storage unchanged, retains no input
pointer, allocates no dynamic memory, and performs no I/O or name resolution.
Character recognition is independent of locale. There is no mutable global
state, and earlier calls cannot affect later results.

## 3. Test integration and reuse

Add the tests to [value_unittests.cpp](../testing/value_unittests.cpp), using
the existing `//argcv/testing:argcv_unittests` target. Keep IPv4 and IPv6 suites
separately identifiable, even where they share supporting code.

The existing `ExpectValidateIpv6` assertion logic and IPv6 G04 octet generator
are the main opportunities for reuse. A shared assertion helper may accept a
validator function pointer while retaining overloads for arrays and
`std::string`. Prefer a small, readable extraction; some duplication is
acceptable, and a general test framework refactor is unnecessary.

Shared cases must carry explicit expected results, and each API must be
checked against its expectation. Merely asserting that the two validators
agree could let the same defect pass both checks. The dotted-decimal
candidates generated by this RFC's G01 can also be tested as IPv6 tails by
prepending `::ffff:`, but this transformation is not valid for arbitrary
cases:

- `1` is not an IPv4 address, whereas `::ffff:1` is valid IPv6 with no
  dotted-decimal tail.
- X13 and X14 in [RFC 004](rfc_004_validate_ipv6_design.md) fail because of
  their IPv6 group counts. Their `192.0.2.1` tails are valid IPv4 inputs.

Any refactoring must preserve all existing RFC 004 coverage, including the
exact-size objects for M02 and X22, zero-compression combinations, mixed
addresses with other prefixes, and the slice boundaries in S19-S23. Retain
the original case IDs or document their mapping to shared cases in test
comments.

## 4. Test specification

### 4.1 Coverage, notation, and assertions

Sections 4.2 through 4.5 are required; Section 4.6 is optional. Each call is
independent unless a sequence is explicitly specified. All calls must satisfy
Section 2.1 and exercise `argcv_validate_ipv4` directly. IPv6 tests cannot
substitute for these calls: the IPv6 parser may reject an input before it
reaches the tail validator.

A shared or generated case may satisfy multiple rows without duplicate calls,
provided it preserves the required backing object and slice. In particular,
equivalent text in different storage does not replace a specified memory
boundary case.

Quoted inputs use C string notation. Quotes and the implicit terminating NUL
are excluded from `len`, and escape sequences denote actual bytes. Explicit
arrays contain only the listed elements, with no implicit terminator.

Assertion helpers must:

- Check that the requested slice is within the backing buffer.
- Snapshot the entire buffer before the call, including bytes outside the
  slice and any string terminator.
- Check the expected boolean result and compare every byte of the buffer
  afterward to verify that it is unchanged.

Pass arrays directly to the validator; do not convert them to strings first.
For string inputs, include the terminator in the snapshot but exclude it from
the input slice. Failure diagnostics must identify the API, case ID, and input,
plus the generated position, octet spelling, or byte value where applicable.

| S18 | `{'1', '.', '2', '.', '3', '.', '1', '0', '0', '0'}` | 0 | 10 | `false` |
| S19 | `{'1', '.', '2', '.', '3', '.', (char)0xEF, (char)0xBC, (char)0x91}` | 0 | 9 | `false` |
| S20 | `{'x'}` | 1 | 0 | `false` |

These cases distinguish the supplied slice from its surrounding storage.
S08-S11 place NUL bytes inside and outside the slice. S12-S18 show how changing
only `len` changes the recognized octet value or address structure. S19
contains the UTF-8 encoding of U+FF11, FULLWIDTH DIGIT ONE, which is not an
ASCII digit.

S01-S04 must each use a separate writable array or allocated block containing
exactly the listed bytes, with the whole object passed as the slice. Do not
replace these objects with parameter records that have spare capacity or with
string copies: the end of the slice must also be the end of readable storage.

S20 uses a separate one-byte array and a pointer one past its end. It checks
that a zero-length slice returns `false` without a read. Call the API directly
for this case so that the existing assertion helper can keep its
`ASSERT_LT(offset, buffer_len)` precondition:

```cpp
TEST(ArgcvValidateIpv4Test, S20EmptySliceAtObjectEnd) {
  char buffer[] = {'x'};
  EXPECT_FALSE(argcv_validate_ipv4(buffer + sizeof(buffer), 0));
  EXPECT_EQ(buffer[0], 'x');
}
```

Run S01-S04 and S20 with `is_asan = true` on platforms that support
AddressSanitizer. Comparing buffer contents detects writes, not reads.
AddressSanitizer may also miss a read beyond the slice when it stays within
the backing object, which is why the exact object sizes matter.

### 4.5 Generated numeric and byte coverage

**G01: Octet spellings at every position.** Start with `1.2.3.4`. Select each
of its four octets in turn and replace that octet with each spelling below,
leaving the other three unchanged. The 20 spellings produce 80 calls in total.

| Expected result | Octet spellings |
| --- | --- |
| `true` | `0`, `9`, `10`, `99`, `100`, `199`, `200`, `249`, `250`, `255` |
| `false` | `256`, `999`, `00`, `01`, `001`, `0000`, `+1`, `-1`, `0x1`, `4294967296` |

The generator may be shared with IPv6's
`G04EveryOctetPositionAndNumericBoundary`. Such reuse must preserve all 80
IPv6 calls as well as the 80 IPv4 calls, with explicit expected results for
both APIs.

**G02: Every byte value at every position.** Start with the seven-byte array
`{'1', '.', '2', '.', '3', '.', '4'}`. At each offset, substitute every value
from `0x00` through `0xFF`, changing only that byte for each call. Pass the
array directly, without adding a terminator. This produces 1,792 calls.

| Replacement offset | Condition for `true` |
| --- | --- |
| 0, 2, 4, 6 | The replacement is an ASCII digit from `0` through `9`. |
| 1, 3, 5 | The replacement is an ASCII dot. |

Every other replacement returns `false`. Derive expectations from this table,
independently of production helpers. The hexadecimal character set used by
IPv6 G03 is not appropriate here. This family covers control characters, NUL,
and every byte with the high bit set at every position.

**G03: Overlong input.** Each of the following returns `false`:

- `1.2.3.` followed by 1024 ASCII `9` bytes.
- `1.2.3.` followed by 1024 ASCII `0` bytes.
- `"255.255.255.255x"`, passing all 16 bytes.

Testing the final octet is sufficient for the long-octet cases. Allocate the
actual input and pass its readable length; an oversized `len` extending past
available storage would violate the contract instead of testing rejection.

### 4.6 Independence between calls (optional)

R01 validates `192.0.2.1`, `256.0.2.1`, `0.0.0.0`, `1.2.3.4.`, and
`255.255.255.255` in that order. Repeat the sequence using the same buffer for
each corresponding input. Both passes must return `true`, `false`, `true`,
`false`, and `true`.

This is an optional regression test: the implementation has neither mutable
global state nor output parameters through which one call could affect the
next.
